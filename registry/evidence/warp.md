## Shape

```
Warp.app  (bundle dev.warp.Warp-Stable, exe Contents/MacOS/stable, ONE process for all tabs)
 |- stable terminal-server --parent-pid N   owns the PTYs -> login shells -> user commands, agent tool commands
 |- stable ripgrep-search / installation-detection-server / minidump-server / remote-server-*   hidden workers
 |- Warp Agent runs IN this process (no separate agent process)
 '- Contents/Resources/bin/oz  bash wrapper: exec -a "$0" ../MacOS/stable "$@"   (Oz CLI, `oz agent run`)

warp  (Warp Agent CLI) = ~/.local/bin/warp -> ~/.warp/tui/current/warp-tui-stable   (curl install)
                         or $HOMEBREW_PREFIX/bin/warp -> warp-tui-stable            (cask warp-agent-cli)
      own PTY + shell child inside; standalone, no app needed

Cloud agents (Automation Platform): Warp or self-hosted infra, nothing local
Third-party agents (Claude Code, Codex, OpenCode, +12) run inside Warp panes: Warp is their HOST, they keep their own rows
```

## Best signal for "a turn is in progress"

The agent backend request holds a macOS activity assertion. `warp_multi_agent_client` builds every request with `.prevent_sleep("Agent Mode request in-progress")`; `prevent_sleep/src/mac.rs` calls `NSProcessInfo.beginActivityWithOptions(UserInitiated, reason)` and ends it on Drop; `http_client` also wraps the response stream so the guard lives while the stream is polled. Both the app and the `warp` CLI use this path. The same code logs `Preventing sleep with reason: ...` / `No longer preventing sleep with reason: ...` at info level, so `~/Library/Logs/warp.log` shows the same edge.

Caveats, all from reading code: it is per request, not per turn, so it can drop while a long local tool command runs between two requests; it is app-wide, not per tab; passive suggestion requests use the same call.

## Waiting on the human

- Internal state is `ConversationStatus::Blocked { blocked_action }`. The app shows it as a tab icon and a "Request" notification.

Only the hosting Warp pane sees it. An outside observer cannot.

## Contradicts common belief

- No separate agent process. The Warp Agent is in the app process, one per app, not one per tab; the process table cannot tell you which tab is working. The CLI is the exception, one process per conversation.
- The Stable app executable is `Warp.app/Contents/MacOS/stable`, not `warp`. `warp` is the standalone Agent CLI (`warp-tui-stable`), a different program with a different DB. The old `oz` binary (`warp-cli` before that) is being deprecated for `warp`; docs say `oz` works through the end of September 2026, which is tomorrow.
- `oz` is not a normal binary: the wrapper `exec -a`s the app binary, so `ps` shows argv[0] as `.../Contents/Resources/bin/oz` while the real image is `MacOS/stable`.
- Warp does export OpenTelemetry, but not for you: OTLP/HTTP traces only, opt-in for cloud-agent runs (`WARP_CLOUD_AGENT_OTLP_ENDPOINT` plus a dispatch token, service `warp-cloud-agent`). A local interactive session exports nothing. The row says `otel: false` on purpose.
- Warp has no hooks for its own agent (no settings file, no events). It is the consumer of other agents' hooks: plugins for Claude Code / OpenCode and a native config for Codex feed it via the OSC 777 protocol. The docs' "notification hooks" page is only OSC 9 / OSC 777 desktop notifications.
- Session data is one SQLite database with an internal Diesel schema (`agent_conversations`, `agent_tasks`, `ai_queries`), not per-session transcript files, and Warp promises none of it (documented=false). Inferred, not verified: conversations are also server-backed (the source has server task ids and cloud handoff), so the local DB may be a partial store.
- Agent-side sleep prevention is Warp's own NSProcessInfo activity, not a `caffeinate` child like Claude Code, so a `child_process` check would find nothing.
- The app's `warpctrl` local-control API sounds like a status source but is dev-channel only and has no agent status actions.
- The probe applies `tree_cpu` to the whole tree, which for Warp includes every shell and command, so it is noisy here. It also ignores `power_assertion`, `waiting_signals` and log lines, so the row's best signals need the Objective-C detector to implement them. `tool_children` and `child_process` were left out because the app always has a `terminal-server` child and the CLI always has a shell child.
